# AI usage disclosure

## Which AI tools were used?

- **Claude Code** (Anthropic): first in a cloud session with access to this repository, later
  in VS Code on my machine, using my Google Cloud credentials (ADC) to deploy.

## How were they used?

I used Claude Code as a pair programmer that did most of the typing, while I made the
product and scoping decisions:

1. **Choosing the challenge.** I gave Claude both briefs and talked through the trade-offs.
   I chose the Spaceship X26 PRMS because its open-ended rules (tier inheritance, the
   Crew Lead invariant, auditing, reporting) leave more room for real design decisions.
2. **Scoping.** I picked TypeScript and asked for a full web application rather than a CLI:
   passengers _book_ resources, and Crew Leads get an admin module. Claude proposed the
   layered architecture (domain / api / web) and the booking model (time slot + capacity +
   check-in), and I approved it before any code was written.
3. **Implementation.** Claude built the system level by level, writing each domain module's
   tests with its implementation and committing per level; the API and web layers followed.
   The commit history shows the levels, not the order within them: tests and code landed in
   the same commits.
4. **Verification.** Claude ran the full suite (lint, typecheck and every test), deliberately
   broke the booking lock to prove the concurrency test can fail, did a production build
   from a clean clone, and walked through the real UI in a headless browser (desktop and
   mobile) to catch integration problems.
5. **Documentation.** The README, design notes and assumptions log were drafted by Claude
   from the decisions made along the way.
6. **Live demo.** I asked for a hosted demo on Cloud Run backed by Firestore, in a Google Cloud
   project I created. Claude added Firestore adapters behind the existing repository ports
   (the domain services did not change), a storage contract suite that runs against both
   backends, an idempotent start-up, a daily demo reset job, and an idempotent deploy script.
   It ran the contract suite and the whole API suite against the real Firestore database, then
   ran the built bundle locally against Firestore. That run caught a production-only crash
   (an ESM named import that the test runner masked), which led to a CI smoke test of the
   built bundle. It also found and removed stray config files that an earlier scaffolding step
   had written to the wrong directory.
7. **Review.** I read the code for its structure and extension points, questioned the
   decisions that weren't obvious, and tested the live demo myself. That produced the roadmap
   and a clearer demand report. See [My review](#my-review).
8. **Mock interview review and fixes.** A mock "tough technical interviewer" review of the
   repository found that the docs promised more than the code guaranteed. Claude worked
   through its findings test-first (each fix started from a failing test, one commit per
   fix) and ran the storage tests against the real Firestore project:
   - Booking safety moved from an in-process lock into storage. Every change is a unit of
     work (a Firestore transaction) that also writes its audit record, so it holds across
     instances, the reset job and deploys. A test with two domain instances on one store
     shows exactly 3 of 10 bookings succeed on a capacity-3 resource; before, 4 did.
   - An account and its password are written together, and storage itself enforces unique
     usernames and three Crew Leads.
   - Booking and audit queries are bounded by time and paged in the database, with the
     composite indexes deployed by the script, instead of reading whole collections.
   - The demand report counts different passengers turned away, by when it happened.
   - Smaller fixes: a stale tier in the header, a late-night default start time in the past,
     the booking policy in `/api/meta`, sign-in timing, average use for resources added
     mid-period, a readiness probe, per-account write limits, and a deploy script that
     refuses uncommitted code.
   - It also found a bug the old seed had hidden: the daily reset (20:00 UTC) asked for slots
     that had already started, so the demo quietly lost its turn-aways.

## My review

I'm responsible for everything submitted, so I reviewed the work in two ways before
submitting.

### Reading the code for structure and extension points

I read the code to understand its overall structure. I concentrated on how it would grow
rather than on every line: where a new booking rule or restriction would go, how storage is
swapped, and where the user experience could improve. What I took away:

- **Layers.** The business rules live in `packages/domain` and know nothing about HTTP or
  storage. The API and the web app sit on top, and storage plugs in behind repository
  interfaces. Adding Firestore showed this works: when it was added, the domain services
  did not change.
- **New booking rules.** `BookingService.book` runs its checks in order: slot limits, tier
  access, the passenger's own overlapping bookings, then capacity. A new restriction, such as
  a daily limit per passenger, would be one more check there. A refusal from it would be
  audited with its rule code automatically, because every booking attempt runs inside
  `AuditTrail.track`.
- **Tunable values.** Durations, the booking horizon and the check-in window are in
  `BookingPolicy`. The demand thresholds are in `ReportService`. Each is defined once and can
  be passed in, but the API uses the defaults.

I then questioned Claude on what the code alone didn't settle. Each question either
confirmed a deliberate decision or became a documented follow-up:

- **How is "exactly three Crew Leads" enforced, when the demo accounts already exist?** The
  roster is configuration (`PRMS_CREW_LEADS`), registered at start-up. There is no API to add
  a lead, and the server refuses to start with two or four. I kept this. Replacing a lead
  isn't supported yet (start-up refuses a fourth), so an audited hand-over is in
  [ROADMAP.md](ROADMAP.md).
- **Is the check-in rule hard-coded?** It is a default in `BookingPolicy`, defined once: from
  15 minutes before the start until the end of the slot. The web app repeated the 15 minutes
  instead of reading it from the API; it now reads the window from `GET /api/meta`.
- **Is the high-usage threshold hard-coded?** It is also a default defined once (75% high,
  40% moderate). The roadmap proposes reading it from configuration or a Crew Lead settings
  page, with every change audited.
- **Can Crew Leads book resources?** No, by design: they are a separate role from passengers.
  I kept this, and it is recorded in [ASSUMPTIONS.md](ASSUMPTIONS.md).

For the user experience, I proposed two features:

- a bird's-eye deck plan showing where each resource is on the ship;
- a timeline in the booking dialog with booked slots greyed out, so passengers don't have to
  find a free slot by trial and error.

I judged both too much for this submission. They are written up in [ROADMAP.md](ROADMAP.md),
with how each would fit the current design.

### Testing the application by hand

Before giving the final sign-off, I used the live demo as a passenger and as a Crew Lead. One
reading I flagged: the resource demand report on the Reports page marked the Luxury O2 Pod as
high demand while showing 7% usage.

The rule was right: six booking attempts had been turned away because the pod was full. But
the page showed only average use, which quiet hours pull down, and its explanation mentioned
only the 75% threshold. I asked for the report to explain itself (commit `db20f8a`):

- a **Peak use** column next to **Average use** (Luxury O2 Pod: 7% average, 100% peak);
- the badge and the shortage banner name the rule that applied ("High · 6 turned away");
- the explanation shows the thresholds the server used, instead of the page repeating 75%.

The rule itself did not change then. The mock review later changed it (step 8): one passenger
retrying could mark a resource as high demand, so it now takes two different passengers.
